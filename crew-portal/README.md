# Crew Portal Packet Lifecycle

This starter implements the server-side packet lifecycle for the AfterJinx pilot against an in-memory SQLite database in tests. SQLite is a reference implementation for local verification. The runtime deployment will use the same behaviors with transactional Postgres and protected object storage.

## Pilot flow

An admin provisions the show and assigns crew or lead roles. A lead opens a draft and adds records for verified files. Publishing atomically replaces the current packet once its files are ready. Crew request the current revision through one stable show slug. A lead can restore a previously published revision and leave a new record of the change.

The portal uses one public event slug to identify a show. Flyer Kit Studio remains a browser-local workspace for draft prompts and creative direction. For a later handoff, use that slug to look up explicitly approved public event fields. Access assignments, draft files, packet paths, and private production information stay on the portal server. The pilot introduces no Studio data imports, shared browser storage, cross-origin calls, or changes to the public event data.

## Starter boundaries

The module accepts principals resolved by a trusted server and file metadata from a verified upload handler. The caller must derive the principal from an authenticated session and verify the stored bytes, size, and PDF format before marking a file ready. Storage object keys are generated by the server. Membership administration belongs to the trusted server or operator.

The next slice needs invited sign-in, a transactional Postgres adapter, the private upload and download handlers, and both phone-friendly views. A storage download must re-check current assignment and publication state before serving bytes. The starter is not a standalone web service. Serve neither the backend source nor a database file as a crew route on the public static site. Use synthetic fixtures until the end-to-end access checks pass.

## Check the starter

Run the following from the repository root with Node 24.

```sh
node --test crew-portal/packet-store.test.mjs
```

For pilot acceptance, prove that uploads write real PDF bytes to private storage and survive a dropped connection. Validate rejection of corrupt or oversized files. Publish a new packet without changing the show URL, reject stale concurrent publishes, and verify rollback history. Check direct download access for signed-out, wrong-show, revoked, and assigned users. Have a lead and crew member complete the publish and download workflow on a real phone.
